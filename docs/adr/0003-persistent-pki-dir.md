# ADR-0003: 自己署名の鍵と証明書の保存先だけを Phase 3 より前に設定可能にする

- 状態: Accepted
- 日付: 2026-10-16
- 関連: [ADR-0001](0001-async-opcua-base.md)、[banto-industrial #634](https://github.com/tyaro/banto-industrial/issues/634)、[banto-industrial #627](https://github.com/tyaro/banto-industrial/pull/627)

## コンテキスト

サーバーは起動のたびに一時ディレクトリへ自己署名の RSA 鍵と証明書を作り、
停止で消していた。SecurityPolicy は `None` なので鍵は通信に使わないが、
async-opcua はアプリケーションインスタンス証明書を前提に起動するため、
生成そのものは省けない。

ハブ（banto-industrial #627）は管理 API で OPC UA を有効化したときに
サーバーを起動し、起動完了を待って応答する。鍵の生成に debug ビルドの
Linux で 2〜6 秒かかり、Windows CI では 10 秒を超えて管理 API の試験が
時間切れになった。鍵の保存先を指定して再利用すると、初回の約 1.8 秒の
あとは約 70ms で起動する（2026-10-16、手元の Linux、debug ビルドで計測）。

`config.rs` は「証明書とセキュリティポリシーの項目は Phase 3 まで置かない」
としていた。保存先の設定はこの方針に触れるため、範囲を決めて例外にする。

## 決定

`ServerConfig::pki_dir`（`with_pki_dir`）を追加する。

- 未設定なら従来どおり、起動ごとに一時ディレクトリへ作って停止で消す。
- 設定すると、そのディレクトリに鍵と証明書が無いときだけ作り、以降の起動では
  読み直す。ディレクトリが無ければ作る。片方だけ残っている（初回生成の途中で
  落ちたなど）ときは、残った方を消して組で作り直す。async-opcua は既存の
  ファイルを上書きしないので、そのままでは組み違いか鍵なしの起動になる。
  存在を確かめられない（権限エラーなど）ときは、何も消さずに起動を止める。
  書き込めないなどで組を作れなかったときも、鍵なしで動かさずに起動を止める
  （async-opcua は鍵なしで続けるが、それでは次の起動でも生成を繰り返す）。
- Unix では、鍵を生成・読み込みする前に秘密鍵の親ディレクトリを `0700` で
  用意し（既存なら絞り）、生成後に秘密鍵を `0600` にする。async-opcua は umask の
  権限で書くが、親ディレクトリを先に閉じるので生成中も他のユーザーは辿れない。
  Windows の ACL は呼び出し側のデータディレクトリに従う。
- 例外は保存先だけにとどめる。SecurityPolicy、ユーザー認証、トラストリスト、
  証明書の更新や失効、ApplicationUri との一致検証は Phase 3 のまま。

## 検討した代替案

- **案A（採用）: 保存先を設定にする。** プロセスの再起動をまたいで再利用でき、
  ハブはデータディレクトリの下に置ける。Phase 3 の証明書管理でも同じ置き場を
  使える。設定の項目が 1 つ増える。
- **案B（不採用）: 同じプロセス内で生成済みの鍵を使い回す。** 設定は増えないが、
  ハブの初回の有効化とプロセスの再起動では従来どおり生成を待つ。CI で時間切れに
  なったのは、まさに初回の有効化だった。
- **案C（不採用）: Phase 3 まで見送る。** ハブの管理 UI が有効化のたびに数秒〜
  十数秒待たされる状態が続く。テストの待ち時間を延ばす対処はすでにしたが、
  製品の応答時間は変わらない。

## 帰結

- 保存先の鍵は、同じ保存先を使う限り使い回される。`application_uri` や
  ホスト名を変えても作り直さない。SecurityPolicy `None` では検証に使わないので
  問題にならないが、Phase 3 で暗号化を開くときは、証明書の内容と設定の一致を
  確かめて作り直す処理を加える。
- 自己署名証明書の有効期限は async-opcua の既定に従う。期限切れの扱いも
  Phase 3 で決める。
- 両方そろっていれば中身は検証しない。壊れたときの復旧は、両方を消して
  起動し直す。同じディレクトリを同時に起動する複数のサーバーで共有しない
  （初回の生成が競合する）。
- 秘密鍵がディスクに残る。置き場のアクセス権は、Unix ではこのクレートが絞る。
  Windows では呼び出し側（ハブのデータディレクトリの ACL）の責任になる。
